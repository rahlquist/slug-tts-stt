5. Phase 3 — source review

5.1 Fixed 30-second Whisper window

Current upstream source was cloned from ROCm/FastFlowLM at commit:

8279cd6786bdd0b4f1ee8e9107c4a436322ce40b
Merge pull request #658 from ROCm/repo-transfer

In src/common/whisper/modeling_whisper_audio.cpp:

const int CHUNK_LENGTH = 30;
const int N_SAMPLES = SAMPLE_RATE * CHUNK_LENGTH; // 480000

if (x.size() < N_SAMPLES)
    x.resize(N_SAMPLES, 0.0f);

int n_frames = (...) / HOP_LENGTH + 1; // 3000

The mel path therefore computes a fixed 128×3000 feature tensor for short input. In the source, the work is clearly separate from encode_audio().

5.2 audio_chunk construction bug

The original code was:

std::vector<float> audio_chunk(l_this_round);
audio_chunk.insert(audio_chunk.begin(),
    this->audio_buffer.data() + current_idx,
    this->audio_buffer.data() + current_idx + l_this_round);

This constructs l_this_round zeroes and then inserts the real audio before them. Measured vector sizes:

InputReal samplesVector after original insert
0.5 s8,00016,000
2.5 s40,00080,000
11 s176,000352,000

This can cause incorrect truncation for longer inputs when preprocessing limits the vector to the 30-second window. It is a real correctness bug, but testing the corrected allocation showed it is not the 2.2-second latency cause.

5.3 Source audio loading

The source decodes the request from memory with FFmpeg, resamples to 16 kHz, converts to mono, and normalizes to float. That path was separately timed.

8. Phase 6 — corrected audio_chunk experiment

The instrumented source was changed temporarily to:

std::vector<float> audio_chunk(
    this->audio_buffer.begin() + current_idx,
    this->audio_buffer.begin() + current_idx + l_this_round);

The corrected vector sizes became 8,000 / 40,000 / 176,000 samples. Encoder timings remained approximately 2.15–2.38 seconds. End-to-end timing did not materially improve. This separates the correctness bug from the performance bottleneck.

9. Phase 7 — power-mode experiment

The temporary instrumented binary was run with --pmode turbo. A 0.5-second request measured approximately 2.37 seconds of encoder time, statistically indistinguishable from performance mode at approximately 2.38 seconds. Turbo mode is not the lever.

13. Final findings

  1. Mel computation for 3,000 frames is approximately 6 ms.
  2. The fixed ~2.2-second cost is the NPU Whisper encoder.
  3. Short input is padded to a fixed 30-second, 3,000-frame representation.
  4. The 30-second boundary produces a large multi-window latency jump.
  5. The original audio_chunk construction doubles the vector and can lose tails on longer input; it should be fixed upstream.
  6. Fixing audio_chunk does not remove the encoder latency.
  7. Proxy, container format, resampling, model reload, and turbo power mode are not the dominant causes.
  8. The most promising optimizations are dynamic/streaming encoder handling, incremental state, or a runtime/model path that avoids a full fixed 30-second encoder invocation.
